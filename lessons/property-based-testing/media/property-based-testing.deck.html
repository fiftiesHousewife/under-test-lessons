What is property-based testing?

  • An example test checks one case its author thought of
  • A property states a rule that must hold for every input
  • A library tries hundreds of inputs to break the rule
An example test checks one case that its author thought of. A property test states a rule that must hold for every input, like, the shares of a bill always add up to the bill. Then a library tries hundreds of inputs, looking for one that breaks the rule.

Our example: splitting a bill

  • Share a bill, in pence, between several people
  • Everyone pays the same, and someone pays what's left over
  • Fair means no two shares differ by more than a penny
Our example splits a bill, in pence, between several people. Everyone pays the same share, and someone has to pay the pennies left over. To be fair, no two people should pay more than a penny apart.

Why examples are not enough

  • Examples only cover the cases someone thought of
  • Bugs live in the cases nobody thought of
  • Many examples passing is not proof that the rule holds
Why are examples not enough? They only cover the cases someone thought of, and bugs tend to live in the cases nobody thought of. A dozen examples passing tells you those dozen cases work. It does not tell you the rule holds.

How jetCheck works

  • Generates random inputs from building blocks such as numbers and lists
  • Checks the property on each one
  • Shrinks a failing input to the smallest one that still fails
jetCheck builds random inputs from simple pieces, like numbers and lists, and checks the property on each one. When an input breaks the rule, jetCheck shrinks it automatically, to the smallest input that still fails. That small case is usually the clearest explanation of the bug.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Build rules every repo shares are written once, in build-logic, and applied to each repo as a plugin
Before we start, a word on how we build. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the build rules that every repo shares, such as code-quality checks and test settings, are written once, in a shared build-logic folder, and applied to each repo as a plugin. That keeps each repo's own build file short.

                When to use property-based testing

                • Calculations, parsing and conversions, where a rule is easier to state than every answer
                • Alongside example tests, not instead of them
                • Keep each smallest failing input as an example test too
                When should you use it? For calculations, parsing and conversions, where a rule is easier to state than every right answer. Use it alongside example tests, not instead of them. And when a property finds a bug, keep the smallest failing input as an example test too.

                Where it came from

                • QuickCheck, by Koen Claessen and John Hughes, introduced the idea for Haskell in 2000
                • jetCheck is JetBrains' library for Java, inspired by QuickCheck and Hypothesis
                • JetBrains uses it to test IntelliJ IDEA itself
                The idea comes from QuickCheck, by Koen Claessen and John Hughes, for the Haskell language, in 2000. jetCheck is JetBrains' property testing library for Java, inspired by QuickCheck and by Hypothesis, and JetBrains uses it to test IntelliJ IDEA itself.
