What is a structured comparison?

  • Compare output as data, not as text: fields, values, lists
  • Field order and spacing don't matter
  • Say exactly which parts may vary, such as an id or a time
A structured comparison checks output as data, rather than as text: its fields, its values, and its lists. The order of the fields and the spacing don't matter. And you say exactly which parts may vary, such as an id, or the time something was made.

Why text comparisons get loosened

  • An id or a time makes the output different on every run
  • A whole-text comparison fails every time, so someone loosens it
  • A loosened test passes whatever the numbers are
Why does this happen? An id, or a time, makes the output different on every run. A comparison of the whole text fails every time, so someone loosens it, to check only a few words. And then it passes, whatever the numbers are.

How JSONUnit works

  • Give it the actual JSON and the JSON you expect
  • Placeholders such as any-string accept any value of that kind
  • A difference names the field, the value expected and the value found
JSONUnit takes the actual JSON, and the JSON you expect. In the expected JSON, a placeholder such as any string accepts any value of that kind. When they differ, it names the field, the value it expected, and the value it found.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Rules every module of the build shares live in build-logic, as convention plugins each module applies
Before we start, a word on how we build. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the rules that every module of the build shares, such as code-quality checks and test settings, are written once, in build-logic, as convention plugins. Each module applies the plugin it needs, instead of one root build file reaching into every sub-project. That keeps each module's own build file short, and says plainly what it uses.

When to compare structure

  • Whenever a test checks JSON or XML: API responses, messages, files for other systems
  • Ignore only fields that must vary, and check they are present
  • For XML, XMLUnit does the same job
When should you use it? Whenever a test checks JSON or XML: API responses, messages, and files for other systems. Ignore only the fields that must vary, and still check that they are there. For XML, XMLUnit does the same job.

Where JSONUnit came from

  • Written by Lukáš Křečan, free under the Apache licence
  • Works with AssertJ, Hamcrest, and plain JUnit
  • XMLUnit does the same for XML, in Java and .NET
JSONUnit was written by Lukáš Křečan, and is free under the Apache licence. It works with AssertJ, with Hamcrest, and with plain JUnit. XMLUnit does the same for XML, in both Java and .NET.
