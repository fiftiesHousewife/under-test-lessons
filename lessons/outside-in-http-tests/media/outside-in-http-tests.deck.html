What is an outside-in test?

  • It tests a running service from outside, through its API only
  • It sends real requests and checks real answers: status, headers, body
  • It knows nothing about the classes inside
An outside-in test checks a running service from the outside, through its API only. It sends real requests, and checks the real answers: the status code, the headers, and the body. It knows nothing about the classes inside.

Our example: a hotel booking service

  • Callers book a room for some nights; a night costs £90
  • A booking for no nights must be refused
  • The answer's status code tells the caller what happened
Our example is a hotel booking service. Callers book a room for a number of nights, and a night costs ninety pounds. A booking for no nights must be refused. And the status code of the answer tells the caller what happened.

Why test from outside

  • Callers only ever see status codes, headers and bodies
  • Inside tests miss the wiring: routes, status codes, headers, JSON
  • Outside tests survive rewrites, so they protect old services while they change
Why test from outside? A service's callers only ever see status codes, headers and bodies. Tests from inside miss the wiring in between. And because outside tests don't depend on the classes inside, they keep working while an old service is rewritten underneath them.

How REST Assured works

  • given: the request, its port, headers and body
  • when: the method and path, such as post /bookings
  • then: what the answer must be, with a clear message when it isn't
REST Assured reads like a sentence. Given the request, with its port, headers and body. When you post it to a path. Then the answer must have this status code, these headers, and this body. When it doesn't, the message says exactly what came back instead.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Rules every module of the build shares live in build-logic, as convention plugins each module applies
Before we start, a word on how we build. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the rules that every module of the build shares, such as code-quality checks and test settings, are written once, in build-logic, as convention plugins. Each module applies the plugin it needs, instead of one root build file reaching into every sub-project. That keeps each module's own build file short, and says plainly what it uses.

When to test from outside

  • For every service other systems call, before changing it
  • Start with the journeys callers rely on most, including the refusals
  • Run the service as it really starts, with stand-ins only for what it calls
When should you test from outside? For every service that other systems call, before you change it. Start with the journeys callers rely on most, including the refusals and errors. And run the service the way it really starts, with stand-ins only for the systems it calls.

  • Brings the readable style of dynamic languages to testing web services in Java
  • Works with any web service, in any language, over HTTP
REST Assured was created by Johan Haleby, and is free under the Apache licence. It brings the easy, readable style of dynamic languages to testing web services from Java. And it works with any web service, written in any language.
