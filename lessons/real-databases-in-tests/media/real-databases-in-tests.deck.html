What is a real database in a test?

  • The test starts the same database production uses, in a container
  • Each test run gets a fresh, empty database, thrown away afterwards
  • Tests that need containers live in their own suite, and skip where there's no container runtime
A real database in a test means the test starts the same database production uses, in a container. Each run gets a fresh, empty database, which is thrown away afterwards. And tests that need containers live in a suite of their own, which skips itself on machines with no container runtime.

Why an in-memory database isn't enough

  • Databases differ: sorting, dates, text, locking, the SQL they accept
  • A test on a different database checks a different program
  • Real databases used to mean shared test servers; containers make them quick and private
Why isn't an in-memory database enough? Databases differ, in sorting, dates, text, locking, and even the SQL they accept. A test on a different database is checking a different program. Real databases used to mean shared test servers, slow and fragile. Containers make them quick, and private to each test run.

How Testcontainers works

  • Name the image, such as postgres:17-alpine, in the test
  • It starts the container before the tests, on a free port, and gives the test its address
  • It stops and removes the container when the tests finish
With Testcontainers, you name the database image in the test. It starts the container before the tests, on a free port, and gives the test its address and password. When the tests finish, it stops the container and removes it.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Rules every module of the build shares live in build-logic, as convention plugins each module applies
Before we start, a word on how we build. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the rules that every module of the build shares, such as code-quality checks and test settings, are written once, in build-logic, as convention plugins. Each module applies the plugin it needs, instead of one root build file reaching into every sub-project. That keeps each module's own build file short, and says plainly what it uses.

When to use a real database

  • For every query, stored procedure and schema change production depends on
  • Keep quick in-memory or fake tests for logic that doesn't depend on the database
  • Machines without containers still run every other test; CI runs the container tests
When should you use a real database? For every query, stored procedure and schema change that production depends on. Keep quick tests, with fakes, for logic that doesn't depend on the database. And machines without containers still run every other test, while the build server runs the container tests.

Where Testcontainers came from

  • Started by Richard North in 2015, free under the MIT licence
  • Now looked after by Docker, with versions for many languages
  • It runs databases, message brokers, and almost anything with a container image
Testcontainers was started by Richard North in 2015, and is free under the MIT licence. It's now looked after by Docker, with versions for many languages. And it can run databases, message brokers, and almost anything else that has a container image.
