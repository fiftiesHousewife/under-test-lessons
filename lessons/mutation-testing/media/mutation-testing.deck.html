What is mutation testing?

  • It tests your tests, not your code
  • Plant one small bug in the code: a mutation
  • Run the tests: if one fails, the bug is caught; if all pass, it survived
Mutation testing tests your tests, not your code. It plants one small bug at a time, for example changing greater than or equal to into greater than. Then it runs your tests. If a test fails, the bug is caught. If every test still passes, the bug survived, and your tests would miss a real bug just like it.

Our example: a shop's discount rules

  • Orders of £50 or more get 5% off
  • Orders of £100 or more get 10% off
  • Loyal customers get 2% more on top
Our example is a small piece of code from an online shop. It works out the discount on an order. Orders of 50 pounds or more get 5 percent off. Orders of 100 pounds or more get 10 percent off. And loyal customers get 2 percent more on top. We'll look at two sets of tests for it: one weak, one strong.

What we'll compare

  • The code under test: the shop's discount rules
  • Weak tests: run every line, but hardly check the answers
  • Strong tests: run the same lines, and check the exact answer at every boundary
Here is what we will compare. The code under test is the shop's discount rules. We have two sets of tests for it. The weak tests run every line, so coverage is 100 percent. But they hardly check the answers. One only checks that the discount is more than zero. One uses an order far from any boundary. One checks nothing at all. The strong tests run exactly the same lines. The difference is what they check: the exact answer, on both sides of every boundary. So when the code gives a wrong answer, a strong test fails.

Why full coverage does not mean you are safe

  • Line coverage counts the lines your tests ran
  • It does not check that any test looked at the result
  • A test with no assertions can still give 100% line coverage
Why do we need mutation testing? Line coverage counts the lines your tests ran. It does not check that any test looked at the result. A test can call the discount calculator, ignore the answer, and still give that line full coverage. If the calculator gave 50 percent off instead of 5, that test would still pass.

How PIT works

  • Changes the compiled bytecode in memory, one mutation at a time
  • Measures line coverage first, then runs only the tests that reach each changed line
  • Reports every planted bug as caught or survived
PIT is the mutation testing tool for Java. It changes your compiled code in memory, one mutation at a time. It measures line coverage first, so for each change it runs only the tests that reach that line. That is what makes it fast enough for whole code bases. Then it reports every planted bug as caught or survived.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Rules every module of the build shares live in build-logic, as convention plugins each module applies
Before we start, a word on how we build. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the rules that every module of the build shares, such as code-quality checks and test settings, are written once, in build-logic, as convention plugins. Each module applies the plugin it needs, instead of one root build file reaching into every sub-project. That keeps each module's own build file short, and says plainly what it uses.

When to use PIT

  • In discovery: measure how far the existing tests can be trusted
  • Then strengthen the tests in key code until PIT catches the planted bugs
  • In pull requests: report surviving bugs on changed code, without failing the build at first
When should you use it? First, in discovery, when you are judging how far the existing tests can be trusted. Coverage tells you what ran. PIT tells you what was checked. Then, strengthen the tests in the code that matters most, until PIT catches the planted bugs there. Later, run it on each pull request, and report the bugs that survive in the changed code, without failing the build at first.

Where PIT came from

  • Mutation testing was first described by DeMillo, Lipton and Sayward in 1978
  • PIT is largely the work of Henry Coles, in Edinburgh, with many contributors
  • First released in 2011; the name first stood for Parallel Isolated Test
The idea of mutation testing goes back to a 1978 paper by DeMillo, Lipton and Sayward. PIT itself is largely the work of Henry Coles, in Edinburgh, with help from many contributors. It was first released in 2011. It began as a tool to run tests in parallel and in isolation, so the name first stood for Parallel Isolated Test. Now, it just stands for PIT.
