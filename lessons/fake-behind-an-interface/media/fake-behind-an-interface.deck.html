What is a fake?

  • A small, working stand-in for a real system, in memory
  • It behaves like the real thing in the ways that matter, such as delivering on commit
  • The code reaches the real system through an interface, so a test can hand over the fake
A fake is a small, working stand-in for a real system, held in memory. It behaves like the real thing in the ways that matter, such as delivering messages only when they are committed. The code reaches the real system through an interface, so a test can hand over the fake instead.

Our example: orders on a message queue

  • Every order is sent to the warehouse
  • Orders of £100 or more are also sent for a fraud check
  • The queue delivers messages only when they are committed
Our example sends orders on a message queue. Every order goes to the warehouse. Orders of a hundred pounds or more also go for a fraud check. And the queue delivers messages only when they are committed.

Why mocks can mislead

  • A mock test lists the calls the code makes, so it repeats the code
  • It can't see behaviour, such as what a commit does
  • It breaks when the code is tidied, even when the results are the same
Why not just use mocks? A mock test lists the calls the code makes, so it repeats the code, line by line. It can't see the system's behaviour, such as what a commit does. And it breaks whenever the code is tidied, even when the results are just the same.

How a fake works

  • It implements the same interface as the real connection code
  • It keeps state: here, messages waiting, and messages delivered
  • Tests check that state: what arrived, not how
A fake implements the same interface as the real connection code. It keeps state: here, the messages waiting, and the messages delivered. And tests check that state: what arrived, not how it got there.

When to use a fake

  • For systems the code talks to a lot: queues, stores, caches, file systems
  • Keep the real connection code thin, behind the interface, and test it separately against the real system
  • An architecture rule can stop other code reaching the real system directly
When should you use a fake? For systems your code talks to a lot: queues, stores, caches and file systems. Keep the real connection code thin, behind the interface, and test that part separately, against the real system. And an architecture rule can stop other code from reaching the real system directly.

Where the idea came from

  • Gerard Meszaros named fakes among his test doubles, in xUnit Test Patterns, in 2007
  • Martin Fowler's article, Mocks Aren't Stubs, explains the difference
  • Fakes need no library: they are ordinary code
Gerard Meszaros named fakes, among other kinds of test doubles, in his book, x Unit Test Patterns, in 2007. Martin Fowler's article, Mocks Aren't Stubs, explains the difference well. And fakes need no library at all: they are ordinary code.
