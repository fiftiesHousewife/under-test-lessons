What is a hard-wired dependency?

  • Code that reaches out for what it needs, instead of being given it
  • A singleton, a static call, or a new inside a method
  • A test can't swap it for a stand-in, so the test runs the real thing
A hard-wired dependency is something code reaches out for, instead of being given it: a singleton, a static call, or a new object made inside a method. A test can't swap it for a stand-in, so the test has to run the real thing: the real network, the real database, the real clock.

  • Lines are priced in pounds, in pence
  • The total is charged in euros, at today's exchange rate
  • The rate comes from the bank's live rate service

Why it matters

  • Old code is full of hard-wired services, clocks and files
  • Tests either can't run, or need the real service: slow, flaky, and sometimes unsafe
  • Passing dependencies in is often the first change that makes old code testable
Why does it matter? Old code is full of hard-wired services, clocks and files. Its tests either can't run at all, or need the real service, which makes them slow, flaky, and sometimes unsafe. Passing dependencies in is often the very first change that makes old code testable.

How Mockito works

  • mock() makes a stand-in for an interface or class
  • when(...).thenReturn(...) says what the stand-in answers
  • verify(...) can check how the code under test used it
Mockito makes stand-ins. You ask it for a mock of an interface or a class. You tell the stand-in what to answer, with when, and then return. And if you need to, you can verify how the code under test used it.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Build rules every repo shares are written once, in build-logic, and applied to each repo as a plugin
Before we start, a word on how we build. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the build rules that every repo shares, such as code-quality checks and test settings, are written once, in a shared build-logic folder, and applied to each repo as a plugin. That keeps each repo's own build file short.

                When to replace a hard-wired dependency

                • Before changing old code that calls a service, a clock, the file system or a static helper
                • Make the smallest change: a constructor parameter, with the old default for production
                • Time is a dependency too: pass in a java.time Clock, never call now()
                When should you do this? Before changing old code that calls a service, a clock, the file system, or a static helper. Make the smallest change you can: a constructor parameter, with the old object as the default in production. And remember that time is a dependency too: pass in a clock, rather than asking for the time.

                Where Mockito came from

                • Started by Szczepan Faber in 2008, building on EasyMock
                • Free under the MIT licence; one of the most used Java libraries
                • PowerMock used to fake statics; it is no longer maintained, and Mockito does it now
                Mockito was started by Szczepan Faber in 2008, building on an older library called EasyMock. It is free under the MIT licence, and is one of the most used Java libraries of all. Old projects may use PowerMock to fake static calls. PowerMock is no longer maintained, and Mockito can do that now, though passing dependencies in is better still.
