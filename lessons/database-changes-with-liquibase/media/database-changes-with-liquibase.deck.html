What is a database changelog?

  • The database's history, written down: one change at a time, in order
  • A tool such as Liquibase applies the changes a database hasn't had yet
  • The same changelog builds every database: developers', test, and production
A database changelog is the database's history, written down: one change at a time, in order. A tool such as Liquibase applies the changes a database hasn't had yet. So the same changelog builds every database: the developers' databases, the test databases, and production.

Why test database changes on the real database

  • A failed change stops a release part way through, on production data
  • Databases accept different SQL and types
  • Changes are hard to undo once they've run, so find out first
Why test changes on the real database? A failed change stops a release part way through, on production data. Databases accept different SQL, and different types. And changes are hard to undo once they've run, so you want to find out first.

How Liquibase works

  • A changelog lists changesets, each with an id and author
  • It records which changesets each database has had, in a table of its own
  • Changes written as Liquibase changes become the right SQL for each database
A Liquibase changelog lists change sets, each with an id and an author. Liquibase records which change sets each database has had, in a table of its own. And changes written as Liquibase changes, rather than raw SQL, become the right SQL for each kind of database.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Rules every module of the build shares live in build-logic, as convention plugins each module applies
Before we start a quick word on how we build these examples. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the rules that every module of the build shares, such as code-quality checks and test settings, are written once, in build-logic, as convention plugins. Each module applies the plugin it needs, instead of one root build file reaching into every sub-project. That keeps each module's own build file short, and says plainly what it uses.

When to test database changes

  • Every change, every time: apply the whole changelog to a fresh real database in the build
  • Prefer Liquibase changes to raw SQL; when raw SQL is needed, test it on every database you run
  • Check the licence: Liquibase 5 uses the Functional Source License; Flyway is an alternative
When should you test database changes? Every change, every time: apply the whole changelog to a fresh, real database in the build. Prefer Liquibase changes to raw SQL, and when you need raw SQL, test it on every database you run. And check the licence: Liquibase five uses the Functional Source License, so confirm your company accepts it. Flyway is another choice, with the same idea.

Where Liquibase came from

  • An open-source tool for database changes, first released in 2006
  • Changelogs can be written in YAML, XML, JSON or SQL
  • Testcontainers gives each test run a fresh, real database to apply them to
Liquibase is an open source tool for database changes, first released in 2006. Changelogs can be written in YAML, XML, JSON, or plain SQL. And Testcontainers gives each test run a fresh, real database to apply them to.
