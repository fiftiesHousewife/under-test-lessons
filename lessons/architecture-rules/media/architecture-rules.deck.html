What is an architecture rule?

  • A test that checks how the code is put together, not what it does
  • For example: the web layer must never use storage directly
  • It reads the compiled classes, so it sees every call, field and parameter
An architecture rule is a test that checks how the code is put together, rather than what it does. For example: the web layer must never use storage directly. The rule reads the compiled classes, so it sees every call, every field and every parameter, and nothing slips past.

Our example: a shop in three layers

  • Web: the pages people see, including an admin page
  • Service: the shop's rules, such as "an order must cost something"
  • Storage: where orders are kept
Our example is a small shop, built in three layers. The web layer has the pages people see, including an admin page. The service layer holds the shop's rules, such as: an order must cost something. And the storage layer is where the orders are kept.

Why unit tests can't see this

  • A shortcut past the service still gives the right answer, for now
  • Each shortcut skips the rules, and makes the next change harder
  • Shortcuts pile up quietly; reviews miss them
Why do we need this? A shortcut past the service layer still gives the right answer, for now. So the unit tests pass. But every shortcut skips the shop's rules, and makes the next change harder. In old code these shortcuts pile up quietly, and reviews miss them.

How ArchUnit works

  • It imports the compiled classes of the packages you name
  • You describe the rule in plain Java: layers, and who may use whom
  • A failure lists every class, field and call that breaks the rule
ArchUnit imports the compiled classes of the packages you name. You describe the rule in plain Java: the layers, and which layer may use which. When the rule fails, it lists every class, field and call that breaks it.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Build rules every repo shares are written once, in build-logic, and applied to each repo as a plugin
Before we start, a word on how we build. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the build rules that every repo shares, such as code-quality checks and test settings, are written once, in a shared build-logic folder, and applied to each repo as a plugin. That keeps each repo's own build file short.

                When to use architecture rules

                • When you agree how old code should be shaped, write it down as a rule
                • On old code, freeze today's breaks so only new ones fail the build
                • Keep rules few and named, so a failure says what was agreed
                When should you use them? Whenever a team agrees how the code should be shaped, write it down as a rule, so the build keeps the agreement. On old code with many breaks already, ArchUnit can freeze today's breaks, so only new ones fail the build. And keep the rules few, with clear names.
