What are recorded HTTP responses?

  • Answers from a web service you don't own, saved as files
  • A local stand-in server replays them to your code
  • Your code can't tell the difference, so tests run without the real service
Recorded HTTP responses are answers from a web service you don't own, saved as files. A local stand-in server replays them to your code. Your code can't tell the difference, so its tests run without the real service.

Why real services make poor test partners

  • They are slow, and down when you need them
  • They need accounts and passwords on every test machine
  • They won't fail on demand, so error handling goes untested
Why not just use the real service? Real services are slow, and they're down just when you need them. They need accounts and passwords on every test machine. And they won't fail on demand, so the code that handles their errors goes untested.

How WireMock works

  • It runs a small web server inside the test, on a free port
  • Each recording pairs a request with the answer to send
  • It can record answers from the real service, or you write them by hand
WireMock runs a small web server inside the test, on a free port. Each recording pairs a request with the answer to send back. You can record the answers from the real service, or write them by hand, including the errors.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Rules every module of the build shares live in build-logic, as convention plugins each module applies
Before we start a quick word on how we build these examples. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the rules that every module of the build shares, such as code-quality checks and test settings, are written once, in build-logic, as convention plugins. Each module applies the plugin it needs, instead of one root build file reaching into every sub-project. That keeps each module's own build file short, and says plainly what it uses.

When to use recorded responses

  • Whenever code calls a service you don't own
  • Record the real answers once, then add the rare ones by hand: errors, timeouts, odd data
  • Check recordings against the real service now and then; contract tests do this between teams
When should you use them? Whenever code calls a service you don't own. Record the real answers once, then add the rare ones by hand: errors, slow answers, and odd data. And check the recordings against the real service now and then. Between teams, contract tests do that job.
