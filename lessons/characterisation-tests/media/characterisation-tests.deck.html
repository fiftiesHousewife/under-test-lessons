What is a characterisation test?

  • A test that records what the code does today, bugs and quirks included
  • It answers "what does it do?", not "what should it do?"
  • Any later change in behaviour shows up straight away
A characterisation test records what code does today, bugs and quirks included. It doesn't ask what the code should do. It asks what it actually does. Once that is pinned down, any change in behaviour shows up straight away.

Our example: a bank statement printer

  • Prints a month of transactions with a running balance
  • Charges a £25 overdraft fee when the balance goes too low
  • Adds interest when the closing balance is over £1,000
Our example is a bank's statement printer, which has run for years without tests. It prints a month of transactions with a running balance. It charges a 25 pound overdraft fee when the balance goes too low, and adds interest when the balance ends the month over 1000 pounds. Nobody remembers every rule it follows.

Why legacy code needs them first

  • Old code often has no tests, and nobody remembers every rule
  • Changing it without tests is guessing
  • Tests that only check "something came back" don't protect you
Why start here? Old code often has no tests, and nobody remembers every rule it follows. Changing it without tests is guessing. And the tests it does have often check only that something came back, which protects nothing.

How ApprovalTests works

  • Run the code and save its whole output as an approved file, next to the test
  • Every later run compares what it receives with what was approved
  • If they differ, the test fails and keeps the received file to compare
ApprovalTests makes this easy. It runs the code and saves the whole output as an approved file, next to the test. Every later run compares what it receives with what was approved. If they differ, the test fails, and keeps the received file, so you can see exactly what changed.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Rules every module of the build shares live in build-logic, as convention plugins each module applies
Before we start, a word on how we build. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the rules that every module of the build shares, such as code-quality checks and test settings, are written once, in build-logic, as convention plugins. Each module applies the plugin it needs, instead of one root build file reaching into every sub-project. That keeps each module's own build file short, and says plainly what it uses.

When to use characterisation tests

  • In discovery and before any change to code nobody can fully explain
  • On outputs that are files, reports, messages or long text
  • A difference is a question, not automatically a bug: approve it, or fix the code
When should you use them? Before you change code that nobody can fully explain, and wherever the output is a file, a report, or a message. When a test fails, treat the difference as a question. If the change is intended, approve the new output. If not, fix the code. Then use mutation testing to check how much the tests really check.

Where they came from

  • Michael Feathers named characterisation tests in Working Effectively with Legacy Code, in 2004
  • ApprovalTests is associated with Llewellyn Falco, with libraries for many languages
  • The same idea is also called golden master or snapshot testing
Michael Feathers named characterisation tests in his 2004 book, Working Effectively with Legacy Code. ApprovalTests is closely associated with Llewellyn Falco, and has libraries for many languages. You may also hear the same idea called golden master testing, or snapshot testing.
