Anti-patterns in existing tests

  • The problem: the tests look better than they are
  • The fix: record them, refuse new ones
  • The tool: ArchUnit
In this lesson, we look at the tests you already have, and the habits that make them look stronger than they are. ArchUnit is a library that reads compiled Java code and checks rules about it. We'll use it to find five kinds of anti-pattern in an old online shop's tests. Then we'll write each one down, and make the build refuse new ones.

Our example: an old online shop's tests

  • A basket: 5% off orders of £50 or more
  • Refunds, to a card or to a gift card
  • Order numbers, and sending paid orders to the warehouse
  • A checkout that reserves stock, adds VAT, takes payment and sends a receipt
Our example is an old online shop. Its basket takes 5 percent off orders of £50 or more. It refunds orders, numbers them, and sends paid ones to the warehouse. Its checkout reserves the stock, adds VAT, takes the payment and sends the receipt. Each part has its old tests, which we won't change.

The tests look better than they are

  • The shop has 13 old tests, and coverage counts every one
  • One checks nothing, one checks only that an answer exists
  • One is switched off, two wait with fixed sleeps, two only pass in order
  • Deleting them would lose what they do pin down
Here is the problem. The shop has 13 old tests, and coverage counts every one of them. But one test checks nothing at all, and another checks only that an answer exists. One has been switched off. Two wait with fixed sleeps, and two only pass in a certain order. We can't trust them as they are. And we can't just delete them, because some of them pin down behaviour that nothing else records.

The fix: record them, refuse new ones

  • An anti-pattern: a habit that makes a test look stronger than it is
  • ArchUnit rules find each one, naming its test, file and line
  • The register: each one written down, with the decision taken on it
  • Then a ratchet: anything not in the register fails the build
An anti-pattern is a habit that makes a test look stronger than it is, also called a test smell. First, ArchUnit rules find each one, and name its test, file and line. Then we write each one down in a register, with its decision. Nothing is deleted. Then the register works as a ratchet, which turns one way only: old findings are allowed, and a new one fails the build.

How it looks

  • "sleeps", test -> sleeps(test) || setUpMethods(...).anyMatch(...)
  • sleeps DispatcherTest.triesAgainWhenTheWarehouseIsBusy fix with the flaky tests
  • [anti-patterns not in the register] expected: 0 but was: 9
  • The rules read the compiled tests with ArchUnit
  • No test is run or changed
How does it look? Each kind is one rule, written with ArchUnit, a library that reads compiled Java classes. The register is a plain text file, one row for each finding, with its decision. And the ratchet's failure says how many findings are missing from the register.

Old tests that check nothing, or are switched off

  • The old tests
  • One checks nothing, one is switched off, one checks only that an answer exists
Now, the old tests themselves. The empty basket test checks nothing. The gift card test was switched off when it started failing, and stayed off. And the place order test checks only that an order came back, whatever is in it.

Old tests that wait, or depend on order

  • Old tests that wait with fixed sleeps, and tests that only pass in order
These tests wait. Each sends an order to the warehouse in the background, then sleeps, for half a second or a whole second, and hopes the work is done. On a busy continuous integration server, it may not be. And the order number tests share one counter, so they only pass in the order the annotation sets.

An old test class that mocks everything

  • An old test class that mocks everything the checkout uses
This test class mocks everything. A mock is a stand-in that records how it was called. Five of them here, one for each thing the checkout uses, so its tests check the calls the code makes, and little of what it does.

The checks: one rule for each kind

  • The checks
  • One rule for each kind, over ArchUnit's view of each compiled test
Here are the checks. Each kind of anti-pattern is one ArchUnit rule about a test: disabled, five or more mock fields, no real assertion, a fixed method order, and a sleep in the test or its set-up. A real assertion is a call to AssertJ, to JUnit's assertions, or to Mockito's verify, but not one that checks only that something exists.

The list, and the ratchet

  • Two tests
  • The list of findings, and the ratchet, which compares them with the register
Two tests use the rules. The first lists every finding, with its test, file and line, and never fails on an old one. The second is the ratchet. It compares the findings with the register, and fails on any finding missing from the register, and on any row it no longer finds.

What these checks leave out

  • Tests that reach shared systems: run them on a machine with no route out
  • Copy-pasted tests: PMD's copy-paste detector, which this build runs already
  • Coverage, reported with and without the tests in the register
There are 7 common kinds. The lesson's checks find 5. Tests that reach shared systems show up when they run on a machine with no route out. PMD's copy-paste detector finds copy-pasted tests, which this build runs already. And report coverage twice, with and without the tests in the register.

When to look for anti-patterns

  • In discovery, before anyone trusts the coverage figure
  • Triage: disabled tests go to the application's owner
  • Waits and order go with the flaky tests
  • We strengthen the rest
  • Nothing deleted before the approval-test baseline exists
When should you look for anti-patterns? In discovery, before anyone trusts the coverage figure. Then triage each one. Disabled tests go to the application's owner, to switch back on or delete. Tests that wait or depend on order get fixed with the flaky tests, and we strengthen the rest. And we delete no test before the approval tests exist, which record what the code does today, since an old test may be the only record of something.

Test smells were first catalogued in 2001, in a paper called Refactoring Test Code, written at a Dutch research institute. Gerard Meszaros's book, xUnit Test Patterns, gathered many more in 2007. ArchUnit has been on Maven Central since 2017. Its own frozen rules work as a ratchet too: they record today's breaks, and fail only on new ones.
