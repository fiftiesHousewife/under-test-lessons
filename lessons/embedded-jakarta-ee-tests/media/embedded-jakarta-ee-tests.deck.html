What is an embedded Jakarta EE test?

  • Old enterprise Java runs inside an application server, which wires its parts together
  • An embedded test starts just the piece it needs, such as the CDI container, inside the test
  • The parts are wired exactly as in production, without deploying anything
Old enterprise Java runs inside an application server, which wires its parts together. An embedded test starts just the piece it needs, such as the container that does the wiring, inside the test itself. The parts are wired exactly as they are in production, without deploying anything.

Why test the wiring

  • In enterprise Java, the container decides what each part gets
  • A new class can change that, without touching the code that uses it
  • Tests on a real server are slow, so they're rare; embedded tests take seconds
Why test the wiring? In enterprise Java, the container decides what each part gets. Adding a new class can change that, without touching the code that uses it. And tests on a real server are slow, so teams run them rarely. Embedded tests take seconds.

How Weld's JUnit support works

  • List the beans the test needs; Weld starts a container with just those
  • Ask the container for a bean, and it arrives fully wired
  • The container stops when the test ends
With Weld's JUnit support, you list the beans the test needs, and Weld starts a container with just those. Ask the container for a bean, and it arrives fully wired. When the test ends, the container stops.

How we build

  • Gradle rather than Maven, with build files written in Kotlin
  • Every library version in one file, the version catalogue: an upgrade is a one-line change
  • Rules every module of the build shares live in build-logic, as convention plugins each module applies
Before we start, a word on how we build. We use Gradle rather than Maven, and write our build files in Kotlin. Every library version sits in a single file, the version catalogue, so upgrading a library is a one-line change. And the rules that every module of the build shares, such as code-quality checks and test settings, are written once, in build-logic, as convention plugins. Each module applies the plugin it needs, instead of one root build file reaching into every sub-project. That keeps each module's own build file short, and says plainly what it uses.

When to use embedded tests

  • For old Java EE and Jakarta EE code: CDI beans, and EJBs with Weld's extra support
  • Before adding a bean that could change what others get
  • Keep server-level tests for what truly needs the server: security, transactions across systems
When should you use them? For old Java E E and Jakarta E E code: CDI beans, and E J Bs too, with Weld's extra support. Use them before adding any bean that could change what others get. And keep the slow server tests for what truly needs a server.

Where Weld came from

  • CDI arrived with Java EE 6, in 2009, and lives on in Jakarta EE
  • Weld is its reference implementation, inside WildFly and other servers
  • weld-junit brings it into JUnit tests
CDI arrived with Java E E six, in 2009, and lives on in Jakarta E E. Weld is its reference implementation, the one inside WildFly and other servers. And the Weld team's JUnit support brings it into ordinary tests.
