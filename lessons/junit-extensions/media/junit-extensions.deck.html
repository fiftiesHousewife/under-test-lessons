JUnit extensions

  • The problem: A fine receipt fails its test
  • The fix: guard settings around each test
  • The tool: JUnit
Our subject this time is JUnit extensions: code that runs around every test, here to put shared settings back afterwards. We'll see one test break another by leaving a setting changed, and an extension that guards the settings.

Our example: a shop's settings

  • Old systems often keep settings shared by the whole program
  • Our shop's settings say whether prices include VAT, and the VAT rate
  • Receipts read them
  • Trade invoices show prices without VAT
Our example is a shop. Like many old systems, it keeps settings shared by the whole program. They say whether prices include VAT, and what the VAT rate is. Shop receipts read those settings. Trade invoices, for business customers, show prices without VAT.

Set-up by hand

  • Tests with set-up by hand
  • The settings set once, before all the tests, and never put back
These are tests with set-up by hand, the way many old tests do it. They set the shop's settings once, before all the tests, and never put them back. The trade invoice test runs first, and leaves VAT switched off. So the receipt test, run second, gets £100 plus VAT, not £120.

The extension

  • A JUnit extension
  • Standard settings before each test, put back after, and a check nothing leaked
Next, a JUnit extension: a small class that JUnit runs around each test. It has 2 methods that JUnit calls back. Before each test, it saves the settings, and sets the standard ones: prices include VAT, at 20%. After each test, it puts back what was there, and fails the test if it left any setting changed, saying which one.

Tests that use it

  • The same tests, with no set-up of their own
  • One line asks JUnit to use the extension
The same two tests, with no set-up of their own. One line, JUnit's extend with annotation, asks JUnit to use the extension. It's written once, and any test class can do the same.

The leak is caught

  • Run both sets of tests against today's trade invoice

By hand, the innocent receipt test fails. The extension fails the test that left the setting changed.

We run both sets of tests against today's trade invoice. The tests set up by hand blame the receipt, whose code is fine. And the failure shows only when the tests run in that order, so it comes and goes. The real culprit, the trade invoice, passes. With the extension, the trade invoice test fails, and names the setting it left changed: it was true, and is now false. And the receipt test passes, because the extension put the settings back.

The fixed trade invoice

  • The trade invoice that writes its own price without VAT, and leaves the settings alone

Every test passes. The extension sets up and cleans up for every test that uses it.

Now the trade invoice that writes its price without VAT itself, and leaves the settings alone. We run the same tests. Every test passes.

When to use an extension

  • When many test classes repeat the same set-up and clean-up: settings, clocks, folders, data
  • In old code with shared state, to find which test leaves it changed
  • Look for one that exists first: JUnit's own temporary folder is an extension
When should you write an extension? When many test classes repeat the same set-up and clean-up, for settings, clocks, folders, or test data. In old code with shared state, to find out which test leaves it changed. And look for one that already exists first. JUnit's own temporary folder is an extension.

Where it came from

  • JUnit 4 had runners and rules for this
  • JUnit 5, in 2017, replaced them with one extension model
  • JUnit 6 is the current generation
JUnit 4 had runners and rules for this, such as the temporary folder rule. JUnit 5, in 2017, replaced them with one extension model. JUnit 6 is the current generation.
